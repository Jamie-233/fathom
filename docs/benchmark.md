# RCA benchmark

Generated by `benchmarks/rca_bench.py` — commit `32db734`, Python 3.13.18, 100 trials per scenario, base seed 1, `device_unreachable` fires after 1 failed poll(s).

**This is a simulated lab.** The simulator and the analyser share an author, so these numbers show that the logic is consistent and where it breaks, not how it would perform on production switches. See the verification table in the README for what has and has not been exercised against real devices.

## How to read the columns

- **Exact**: the open incident points at the right place *and* has the right kind and confidence (a dead multi-homed switch → `device`/high; a cut single-homed uplink or a dead single-homed switch → `link`/medium, because those two look identical from the poller; a failed redundant link → `link`/high "redundancy lost"; CPU, CRC and BPDU faults → the matching local incident).
- **Located**: the right place, but the kind or confidence differs from the expectation above (includes Exact).
- **Missed at end / never seen**: injected faults with no incident pointing at them when the window ended, and those that never produced one at any cycle (the difference is incidents that opened and then closed again).
- **Trials with a false incident**: trials that ended with an open incident that matches no injected fault.
- **Alerts → incidents**: mean number of firing alerts versus incidents an on-call engineer would see.
- Intervals are 95% Wilson confidence intervals over faults.

Ground truth is taken from the lab (what is really unreachable), not from the RCA output. Fault targets, lab seeds and (in the random topology runs) the network itself change on every trial. `noise` is the probability that a device's poll is lost in a cycle.

## Summary

| | bundled lab (9 devices) | random campuses |
|---|---|---|
| Faults located, no poll loss | 1100 / 1100 | 1166 / 1166 |
| Faults located, 2% poll loss | 1086 / 1100 | 1157 / 1167 |
| Exact, no poll loss, all scenarios except "cut all uplinks" | 1000 / 1000 | 1000 / 1000 |
| Exact, 2% poll loss, same scenarios | 964 / 1000 | 972 / 1000 |
| Healthy network, 20 cycles, 2% poll loss: runs that opened a false incident | 100 / 100 | 99 / 100 |

- **Grouping is where the value is.** Powering off a distribution switch raises 5.0 alerts on average in the bundled lab (5.4 in random campuses) and Fathom turns them into one incident. Two simultaneous faults: 6 alerts become 2 incidents.
- **Against naive pickers.** For faults whose symptoms outnumber the cause, paging the device of a random alert names the right place 20% of the time for a distribution switch, 25-28% for a core or edge switch and 41-51% for an access switch; Fathom names it in 98-100% of trials. For a single link cut or a local fault (CPU, CRC, BPDU guard) the alert already sits on the cause, so the baselines tie with Fathom and the RCA adds only the grouping.
- **Detection time.** Structural faults open an incident after one polling cycle; CPU needs a median of 4 cycles and CRC errors 2, because those rules require the condition to persist (the pending period). One cycle is 30 simulated seconds.

## Findings

These are the places where the analyser or the rules do something an on-call engineer would not want. Each is reproducible with the quoted seed.

**1. A switch that is alive but has lost every uplink is declared dead, with high confidence.**
Cutting all infrastructure uplinks of a powered distribution switch produces `device:<name>` / *high* ("<name> is down") instead of the honest "link or device, indistinguishable from outside" that a single cut uplink gets. In the bundled lab this happens in 100 of 100 trials; in random campuses in 34 of 100, which are exactly the trials where the cut really isolated the switch (in the other 66 a dual-homed access switch keeps it reachable and two separate redundancy-lost links are reported correctly). Cause: `Topology.device_dead()` asks whether every *visible* neighbour sees its link as down, which is also true for a live switch whose visible neighbours are all across the cut links. From the poller a dead switch and an isolated one look the same, so this should be medium confidence too. Reproduce: seed `1:lab:0.0:link_cut_all_uplinks:0`.

**2. One lost poll opens a false incident.**
`device_unreachable` fires after a single failed poll. With 2% of device polls lost, every 20-cycle run on a healthy network paged at least once (388 incidents in 100 runs on the bundled lab, 531 on random campuses), and 14-18% of runs with a real fault also carried a false `device:X [low]` incident. Requiring two consecutive failed polls (`--unreachable-cycles 2`, results at the end of this file) cuts healthy runs with a false incident from 100 to 10 and from 99 to 9, and runs with a real fault from 140 to 16 and from 182 to 17 (out of 1000). The cost: a real outage can show misleading link-level incidents for one cycle before the device-level incident replaces them (powering off `dist-02` shows two separate "redundancy lost" links on cycle 1 and `device:dist-02` / high on cycle 2). The default has not been changed.

**3. A lost poll also erases real local alerts for a few cycles.**
With a CRC alert firing on `acc-04`, one lost poll resolves it (the rule only looks at reachable devices), raises `device_unreachable` for `acc-04`, and the CRC alert comes back only after its two-cycle pending period. With 2% loss this left 14 of 1100 and 10 of 1167 injected faults without an open incident when the window ended, although every fault was seen at some point. The debounce does not help because the cause is the resolve path. Holding the last known state for a device that missed one poll, instead of treating it as healthy, would fix both this and finding 2.

**4. A lost poll can also change a correct classification.**
When a neighbour's poll is lost, fewer neighbours are visible, and a dead distribution switch can be reported as `link` / medium instead of `device` / high (seed `1:random:0.02:power_distribution:1`). It is still located correctly, and medium is the honest answer for the evidence it had, so this is a limit rather than a bug.

## What this does not show

- The simulator and the analyser share an author. Perfect scores in the clean runs show consistency, not correctness against real equipment, and the real-device column of the verification table in the README is still empty.
- Topologies are campus trees with two cores, the poller behind the core, and at most four distribution switches. There is no routing protocol, spanning tree, ACL, partial degradation (loss, flapping) or multiple pollers.
- Ground truth is defined by lab reachability. Cases that this definition cannot express (a switch that is up but forwarding wrongly) are not tested.
- 100 trials per scenario; the intervals show the uncertainty. Differences of a few percentage points between rows are not significant.

## Reproduce

```bash
pip install -e '.[dev]'
python benchmarks/rca_bench.py --trials 100 --seed 1 --noise 0 0.02 --out docs/benchmark.md   # about 4 minutes
python benchmarks/rca_bench.py --trials 100 --seed 1 --noise 0.02 --unreachable-cycles 2       # the debounce variant
```

Every trial is derived from a seed string such as `1:random:0.02:power_distribution:1`, so any case quoted below can be re-run on its own with `run_trial` in `benchmarks/rca_bench.py`.
